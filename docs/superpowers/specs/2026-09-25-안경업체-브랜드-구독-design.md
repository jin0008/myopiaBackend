# 안경업체(브랜드) 구독 설계

2026-09-25

## 왜 만드는가

지금 광고는 **시설 하나 단위**다. 안과·안경원이 자기 가게를 프리미엄으로 올린다.
여기에 **브랜드 단위**가 더해진다. 에실로 같은 안경 업체가 구독하고, 그들이 준
취급점 목록(스텔리스트 기준 약 800곳)이 지도에서 한꺼번에 혜택을 받는다.

브랜드가 돈을 내고 얻는 것은 셋이다.

- 지도에서 **브랜드로 걸러 보기** ("스텔리스트 취급점만")
- 취급점에 **브랜드 마크**
- 매장별 **블로그 링크**

## 범위

**만든다**
- 브랜드·취급점 데이터 모델과 매칭
- 운영자 화면: 브랜드 관리, 취급점 업로드, 매칭 결과 확인
- 안경원 파트너의 **취급 제품 태그** 관리
- 앱: 브랜드 필터·마크·블로그 링크
- 광고 순환 노출과 노출량 집계

**만들지 않는다**
- **브랜드 포털(브랜드 로그인)** — 에실로가 파일로 목록을 주기로 했다. 800곳을
  직접 관리하러 들어올 이유가 없다. 요구가 생기면 그때 만든다.
- **안경원 프로필**(소개·배너·사진) — 노출될 화면이 없다. 안경원을 누르면 뜨는
  것은 명부 기반 바텀시트뿐이고, 파트너가 채울 칸이 하나도 없다. 병원은
  치료탭이라는 화면이 있어 프로필이 필요하지만 안경원은 아직 없다.
- **재고 현황** — 안경원이 매일 갱신할 리 없다. 틀린 재고는 없느니만 못하고,
  손님이 헛걸음하면 우리 탓이 된다.
- 결제 연동 — PG 가 정해지지 않았다. 아래 "결제" 참고.

## 데이터 모델

### 새 표

```
brand           브랜드 자체. 이름, 로고(지도 마크), 소개, 구독 기간.
                주소·좌표가 없다 - 브랜드는 장소가 아니다.

brand_shop      브랜드 ↔ 안경원. 이 프로젝트의 심장.
  brand_id
  license_no    optical_shop 을 가리킨다
  blog_url      매장별 블로그
  status        "active" | "ended"
  matched_by    "license_no" | "name_address" | "manual"
  source_name   브랜드가 준 원본 상호
  source_address 브랜드가 준 원본 주소

optical_tag     안경원이 스스로 신고한 취급 제품.
  license_no
  product       "myosmart" | "stellest" | "zeiss" | …
```

### 왜 이렇게 나누는가

**브랜드를 `hospital_profile` 에 넣지 않는다.** 그 표는 카카오 place id 에 unique 가
걸려 있는데 브랜드에는 줄 값이 없다. 가짜 값을 채우면 그 뒤로 모든 조회가 그
거짓말 위에서 돈다.

**`status` 로 남기고 지우지 않는다.** 계약이 끝난 매장을 지우면 왜 사라졌는지 알
방법이 없다. `eye_clinic.closed_at` 과 같은 이유다.

**`matched_by` 와 `source_*` 를 남긴다.** 800곳 중 자동으로 안 붙은 것은 사람이
손으로 붙인다. 어느 것이 자동이고 어느 것이 수작업인지 구분되지 않으면, 나중에
매칭 규칙을 고쳤을 때 무엇을 다시 검증해야 하는지 알 수 없다.

### 인증과 자가 신고를 구분한다

같은 사실에 주인이 둘이다.

```
"이 매장은 스텔리스트를 취급한다"
  ← brand_shop     브랜드가 보증 (브랜드가 돈을 냄)
  ← optical_tag    매장이 신고   (매장이 돈을 냄)
```

| | 근거 | 앱에서 |
|---|---|---|
| 브랜드 인증 | `brand_shop` | 브랜드 마크 + **필터 대상** |
| 자가 신고 | `optical_tag` | 상세시트에 텍스트로만 |

이 구분이 없으면 안경원이 스스로 체크하는 것만으로 브랜드 마크를 얻고, 브랜드가
돈을 낸 의미가 사라진다.

## 매칭 — 가장 위험한 부분

브랜드가 준 목록을 `optical_shop`(10,227곳)에 붙이는 일이다. **이 프로젝트의 성패가
여기서 갈린다.**

우리 열쇠는 **인허가 관리번호**(`PHMB` 로 시작하는 25자리)다. 브랜드가 그 번호를
주면 1:1 로 떨어진다. 주지 않으면 상호·주소로 대조해야 하는데, 안경원은
`○○안경` 같은 흔한 상호가 많아 병원보다 훨씬 어렵다.

**2026-09-25 현재 에실로에 확인 요청한 상태다.** 답에 따라 수작업 분량이 정해진다.

매칭은 자동으로 확정하지 않는다. 결과를 세 갈래로 나눠 운영자에게 보여준다.

- **확실** — 인허가번호 일치. 그대로 붙인다.
- **후보** — 상호·주소가 비슷하다. 사람이 고른다.
- **없음** — 못 찾았다. 손으로 지정하거나 브랜드에 되묻는다.

퍼지 매칭은 오늘 병원 검색에서 겪은 그대로 어렵다 — 띄어쓰기(`눈편한 성모안과` vs
`눈편한성모안과`), 꼬리표(`안과` vs `안과의원`), 주소의 층수. 안경원에서도 같은
방식으로 견준다(공백 제거, 전화번호 일치).

### 명부가 낡아 있는 문제

`optical_shop` 은 2026-09-08 이후 갱신되지 않았다. 원본(행정안전부 안경업
인허가)의 제공 서버가 내려갔기 때문이다. 자세한 것은 아래 "대기 중인 것".

브랜드 매칭은 이 명부 **위에 얹힌다**. 명부가 낡으면 폐업한 매장에 브랜드 마크가
계속 붙는다. 명부 갱신이 이 기능의 전제다.

## 화면

### 운영자

| 화면 | 하는 일 |
|---|---|
| 브랜드 관리 | 브랜드 생성(이름·로고·소개), 파트너 계정 연결, 구독 기간 |
| 취급점 업로드 | 브랜드가 준 파일을 올려 매칭 실행 |
| 매칭 결과 | 확실/후보/없음 세 갈래. 후보는 고르고, 없음은 손으로 지정 |
| 취급점 목록 | 블로그 URL 편집, 계약 종료 처리 |

**매칭 결과 화면이 가장 많이 쓰인다.** 인허가번호가 오면 거의 안 쓰이고,
상호·주소만 오면 여기서 수백 건을 처리한다.

### 안경원 파트너

프로필 편집기(카카오 장소·진료시간·의사·치료항목)를 **감춘다**. 병원 것이다.

남기는 것은 둘이다.
- 프리미엄 신청 (기존 `PartnerPromotions`)
- **취급 제품 태그** — 안과의 치료항목에 대응한다

### 앱

- 찾기탭 **브랜드 필터** — "스텔리스트 취급점만"
- 목록·지도의 **브랜드 마크**
- 상세시트에 **블로그 링크**와 자가 신고 취급 품목

## 광고 노출 규칙

### 이미 있는 방어 장치

```js
const AD_SLOTS = 3;       // mobile.ts
const AD_RADIUS_KM = 5;
```

한 지역에 서른 곳이 구독해도 상단에는 세 개만, 가까운 순으로 나온다. 밀집으로
첫 화면이 광고로 덮이는 일은 이미 막혀 있다.

### 반경 구독권과 순환 노출

반경별 구독권(2km/5km/10km)은 업체에게 설명하기 쉽다. 다만 반경만으로는 밀집이
풀리지 않는다 — 강남에서 서른 곳이 모두 2km 권을 사면 그 2km 안에서 세 자리를
두고 경쟁하는 것은 그대로다.

그래서 **파는 단위를 자리가 아니라 노출량으로 본다.** 슬롯이 넘치면 순환시키고,
각자 실제 노출 수를 보장한다. `promotion_stat_daily` 가 이미 노출·클릭을 세고
있어 "이번 달 1,200회 노출" 같은 실증을 낼 수 있다.

자리는 세 개뿐이라 팔수록 서로 희석되지만, 노출량은 정직하게 나눠진다.

**순환 기준은 "덜 나간 순"이다.** 조회 시점에 후보가 슬롯보다 많으면, 그날 노출
수(`promotion_stat_daily`)가 적은 업체를 먼저 올린다. 무작위로 섞는 것보다 나은
점이 둘이다 - 장기적으로 노출이 고르게 수렴하고, "왜 우리만 덜 나오냐"는 물음에
숫자로 답할 수 있다. 같은 노출 수면 가까운 순으로 가른다.

검토했다가 택하지 않은 것:
- **동 단위 독점권** — 밀집이 원천 차단되고 값도 비싸지지만, 팔 수 있는 수에
  상한이 생겨 매출이 제한된다. 먼저 산 곳이 계속 쥐어 뒤에 온 업체가 살 게 없다.
- **밀도별 가격 차등** — 공정하지만 가격표가 복잡해져 영업이 어렵다.

## 결제

PG 가 정해지지 않았다. **PG 와 무관하게 먼저 만들 수 있는 것만** 한다.

- 가격표 (`주체유형 × 기간 → 금액`). 병원·안경점·안경업체가 값이 다르다.
- 주문·결제 기록 표. `provider`, `provider_tx_id`, 금액, 상태, 원본 응답.
- 웹훅 수신 골격과 멱등키(`provider` + `event_id` 유니크). 모든 PG 가 웹훅을
  중복 전송하므로, 이 부분은 PG 가 누구든 똑같이 필요한 우리 코드다.

만들지 않는 것: **PG 추상화 인터페이스.** 구현체 하나짜리 인터페이스는 실제 PG 의
모양과 안 맞아 두 번 일하게 된다.

`promotion_request` 승인 로직은 이미 트랜잭션에서 멱등하게 돌아간다. 웹훅이 붙으면
그것을 함수로 떼어 재사용한다.

## 대기 중인 것

이 설계를 막고 있는 외부 답변 둘.

**① 에실로 — 취급점 목록에 인허가번호가 있는가**
매칭 난이도와 수작업 분량이 여기서 정해진다. 계약 종료 매장을 어떻게 알려줄지도
함께 확인해야 한다.

**② 안경원 명부를 다시 받는 경로**
`optical_shop` 이 2026-09-08 이후 멈춰 있다. 원본은 행정안전부 안경업 인허가
표준데이터이고, 데이터셋에 적힌 다운로드 주소
(`https://file.localdata.go.kr/file/optical_shops/info`)가 403 이다. 스크립트도
실제 브라우저도 같다. `localdata.go.kr` 전체가 응답하지 않는다.

확인해서 지운 경로:

| 시도 | 결과 |
|---|---|
| odcloud 자동 API 변환 | 외부 호스팅이라 대상 아님 |
| 심평원 API | 안경원은 요양기관이 아님 — 이름 검색 0건 |
| 카카오 API 비교 | 색인이 불완전해 폐업 판정 불가 |
| 지자체 개별 데이터셋 | **인허가 관리번호가 없다** |

새 출처를 받을 때 **관리번호 체계가 `PHMB` 그대로여야 한다.**
`facility_promotion.key` 와 `hospital_account.facility_key` 가 이 번호를 참조한다.

## 단계

한 번에 다 만들지 않는다. 앞 단계가 뒤 단계를 막는다.

**1단계 — 지금 할 수 있는 것** (외부 답변과 무관)
- `brand`, `brand_shop`, `optical_tag` 표와 마이그레이션
- 안경원 파트너에서 병원 프로필 편집기 감추기
- 안경원 취급 제품 태그 관리 화면
- 운영자 브랜드 관리 화면(생성·계정 연결)

**2단계 — 에실로 답변이 온 뒤**
- 취급점 업로드와 매칭
- 매칭 결과 확인 화면
- 매칭 난이도가 여기서 정해지므로, 답을 보기 전에 만들면 헛일이 된다

**3단계 — 명부 갱신 경로가 뚫린 뒤**
- 앱의 브랜드 필터·마크·블로그 링크
- 낡은 명부 위에 브랜드 마크를 띄우면 폐업한 매장에 광고가 걸린다

**4단계 — PG 가 정해진 뒤**
- 순환 노출과 노출량 리포트
- 결제 연동

## 검증

- 매칭 규칙은 순수 함수로 떼고 assert 로 덮는다. 오늘 `mergePlaces`,
  `decideClosures` 에서 쓴 방식과 같다.
- 브랜드 마크가 `brand_shop` 에서만 나오는지(자가 신고로는 안 나오는지) 확인한다.
- 순환 노출은 같은 지역에서 여러 번 조회해 슬롯에 오르는 업체가 바뀌는지 본다.
